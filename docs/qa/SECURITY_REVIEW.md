# Security review (bounded, 2026-10-13)

A bounded security review of the tree at SHA `5aebc7c8` was done on 2026-10-13.
This page records the findings and what happened to each. It is a summary of the
reviewer's report, not the report itself, and it is not a penetration test: no
exploitation against the running lab is recorded here. Finding identifiers (A1, M1,
B3, ...) are the reviewer's. The reviewer's file and line references were not
supplied to this page; the file references below were found by reading the tree
now and may move.

| B6 (C1, C2, C3) | Internal error text reached public responses: the owner's `result.error` was `str(exc)` (engine host names, driver messages, text written by the engine), the pricing 503s repeated the reason of SPACE / SPHERE (one of them to anonymous callers), and the gateway had no `correlationId` | **C1** (`core/public_errors.py`): an unhandled exception is a 500 `internal_error` with a fixed `detail`; every 5xx document carries `correlationId`; 4xx are unchanged. **C2**: `result.error` of a failed job is a fixed sentence of the closed catalog `JOB_FAILURES` for a stable `result.code` (`engine_unreachable`, `engine_timeout`, `engine_rejected`, `engine_protocol_error`, `engine_failed`, `engine_endpoint_invalid`, `engine_error`, `credential_unavailable`, `bim_evaluation_failed`, `job_input_invalid`, `registration_changed`, `lease_lost`, `job_abandoned`, `internal_error`) plus `result.correlationId`; the shape of the result is unchanged. `RemoteEngineError` carries `code` and its message goes to the log only; the engine's own text is cut at 1 KiB with a mark. | B4 (C4) | If BIM failed during the re-evaluation the job became FAILED and the engine's raw result was lost (a solve of up to 1800 s); the failure had no code of its own; nothing could re-evaluate without solving again; BIM was called with the job row locked | The raw answer is written to the new table `job_engine_evidence` (migration `a5b6c7d8e9f0`, after `f2a3b4c5d6e7`; at most 4 MiB, the bound of `v1/remote.py`) and committed **before** BIM is called (`services/execution.py`, `settle_engine_answer`), so BIM runs with no row lock; the lease is taken again afterwards and `cancellation_requested` is checked again. A BIM failure leaves the job FAILED with the stable `result.code` `bim_evaluation_failed`, the fixed sentence of the catalog and `result.evidence = {id, digest, expiresAt}` (never the body); something not evaluated is never recorded as valid. Any success deletes every evidence row of the job; a lost lease deletes the worker's own row. `POST /v1/jobs/{id}/reevaluate` (`routes/jobs.py`): the owner with MEMBER (`require_work_role`), an API key with `engines:execute` (a read-only key and a VIEWER's key are refused), `404` to anyone else; `409` for `job_in_study`, `job_already_retried`, `cancellation_requested`, `job_not_reevaluable`; `410 evidence_expired`; `503 bim_evaluation_failed` if BIM fails again, with the job and its evidence untouched. The move FAILED to COMPLETED is a compare-and-set `UPDATE` (state, code, evidence row of the current attempt), audited as `job.reevaluated`. Retention `EVIDENCE_RETENTION_DAYS` (default 14, maximum 90); the reconciler deletes expired rows in batches of 500 (`SKIP LOCKED`, database clock). Tests: `tests/test_job_evidence.py` (SQLite), `tests/concurrency/test_job_evidence_pg.py` (PostgreSQL, two simultaneous retries, retry or worker against a cancellation, no row lock during BIM), and the former `xfail` of `tests/analysis_b3_b4_b6/test_analysis_b4_reevaluation_failure.py`, now normal tests. **Limits:** there is no `GET /evidence` (the body of an engine published by another owner can carry that owner's text); the downgrade of the migration drops the table and with it every answer still kept; the evidence is gone after the retention (`410`), and then only `retry` (which solves again) is left; a job of a study run cannot be re-evaluated on its own; an answer over 4 MiB is not kept; if the evidence cannot be written the evaluation goes on without it, and a BIM failure then leaves no evidence to retry from |
| B3 (C5) | The remote job of an attempt that lost its lease kept running: `_requeue` and `_fail_abandoned` cancelled nothing, the id of an attempt was overwritten by the next one, and `DELETE` was sent to any engine, declared or not (and no engine in the tree implements it) | **Best effort, conditioned on a declared capability, with fencing; not exactly-once.** The capability is declared in the registration (`spec.extensions.cancellation = {supported: true, idScope: "attempt"}`; the schema and the manifest are unchanged) and is trusted only if the deployment's pinned OpenAPI describes `DELETE` on the job path (otherwise it is off, logged and shown as a `disabled` check, and the registration keeps its state). New table `job_engine_attempts` (migration `b6c7d8e9f0a1`, after `a5b6c7d8e9f0`): the id and endpoint of every attempt, and the state of its cancellation. **One door** (`services.execution.cancel_engine_attempts`, the only caller of the transport) for the three paths of the worker and for the reconciler's step; it reads the attempt's row, not a local variable. Rules (`jobs/remote_attempts.py`, `decide`): no capability, no `DELETE`; attempt `k` is cancelled only if the job is terminal, or is not running, or the running attempt registered a **different** id; if the running attempt has no id yet it is deferred with backoff and skipped after `REMOTE_CANCEL_DEFER_LIMIT` (5) deferrals, never sent blind; the running attempt and an id shared with a newer attempt are never cancelled; without `idScope: attempt` only a terminal job; no `DELETE` (and no credential decrypted) if the registration now points at another endpoint. The sweep only marks (no network); after its commit the step claims a bounded batch (compare-and-swap, `SKIP LOCKED`), sends with 3 s timeouts and bounded concurrency, and retries network errors with backoff up to `REMOTE_CANCEL_MAX_ATTEMPTS` (8). The lease-token fencing is untouched: a late result is still discarded. The write of an engine id runs shielded from cancellation. Tests: `tests/test_remote_cancel.py` (SQLite, local HTTP doubles, the rules over every combination of states), `tests/concurrency/test_remote_cancel_pg.py` (two replicas; for the lab), the former `xfail` of `tests/analysis_b3_b4_b6/test_analysis_b3_lease_loss.py`, now normal tests, and `tests/test_job_leases.py` (its fixtures declare the capability). **Limits:** no real engine was tested and none implements `DELETE` today, so in practice nothing is sent yet; how a real engine reacts (including one that reads `DELETE` as "delete the result") is unknown; the engine still runs the work at least once and two solves overlap until the cancellation, if any, arrives; **the slow worker keeps waiting** for its engine up to `ENGINE_SOLVE_TIMEOUT_S` (1800 s by default) because `leases.beat` does not interrupt the solve (its test stays `xfail`); if the gateway crashes between the engine's `202` and the commit of the id there is nothing to cancel; a 404/405 is not retried; the downgrade of the migration drops the ids and the pending cancellations |
