# Remote cancellation, end to end, on the bundled engines (G1)

`docs/qa/ENGINE_CANCELLATION.md` describes the engine side (`engines/minizinc-csp` stops the solver on `DELETE`), and
`jobs/remote_attempts.py` + `services/execution.py` the gateway side (a best-effort `DELETE`, fenced per attempt). Between
the two there was a gap: the gateway reads the capability from the **registration** (`spec.extensions.cancellation`, backed
by a `DELETE` in the registration's OpenAPI), and the registration of a bundled engine, generated by
`services/engines.py::builtin_engine_registration`, declared nothing. So the gateway never sent the `DELETE` to a bundled
engine. This change closes that gap for the engines that always implement it and adds a laboratory probe that checks the
whole path.

## What the bundled registration declares now

| Engine | `spec.extensions.cancellation` | `DELETE` in `spec.openapi` | Why |
| --- | --- | --- | --- |
| `minizinc-csp` | `{"supported": true, "idScope": "attempt"}` | yes (`/internal/v1/jobs/{id}`, 200/202/404) | asynchronous and cancels for real, always |
| `random-search` | none | no | no `DELETE` |
| `many-heuristic`, `evolutionary-heuristics` | none **by default** | no | the `DELETE` exists only with `ENGINE_JOB_MODE=async` (default `sync`); the registration cannot know the mode |

Two things are needed, not one: the declaration **and** the operation in the OpenAPI. The `bim-engine/v1` protocol document
has no `DELETE`, and `engine_registry.cancellation_capability` turns the capability off when the registration's OpenAPI
does not describe it, so the declaration alone would be logged as "declared but off" and nothing would be sent.

* The engine is identified by its manifest `metadata.name`, in the explicit table `engines.BUILTIN_CANCELLATION`; never by
  a heuristic.
* An engine outside the table is enabled by naming it in **`ENGINE_CANCELLATION_BUILTIN`** (comma-separated manifest
  names, empty by default), in the same deployment that sets `ENGINE_JOB_MODE=async` for it. The names are validated: a
  name that is not shaped like an engine name, or that has no manifest in the catalog, is refused (logged once at ERROR) and
  not enabled, so a typo can only leave cancellation off. The variable only **adds** to the table.
* The registration is immutable by digest. Declaring (or no longer declaring) the capability changes the
  `+builtin.<digest>` version. Engines that declare nothing keep exactly the registration they had.

### Deployment note

A job pins the exact registration it was accepted with (`original_request.registration`, and the same reference in
`provenance`). After deploying this change the `minizinc-csp` registration has a new version, so a **queued** job accepted
before the deployment no longer matches (`installed_builtin_registration` returns `None`) and fails with
`registration_changed`, as it does for any change of a bundled engine's endpoint. The same happens, for the Java engines,
when `ENGINE_CANCELLATION_BUILTIN` is changed.

Operations: before rolling out a change that alters a bundled registration (this one, a new `ENGINE_CANCELLATION_BUILTIN`,
a different engine URL), **drain the queue** (stop accepting work and let queued jobs run, or cancel them) or accept that
the jobs still queued fail with `registration_changed` and are submitted again (`POST /v1/jobs/{id}/retry` makes a new job
against the current registration). A job already `running` keeps the registration it started with and is not affected.

A queued job is **not** re-bound to the current version by the code. It would mean rewriting the job's pinned reference in
`original_request` and in `provenance` (and in the `JobProvenance` document with its digest), which are the record of what
the user was promised when the job was accepted; the registration changed (a different `DELETE` capability and OpenAPI), so
that record would no longer describe what ran. This stays an operational step, deliberately.

## The probe: `openbinding-gateway/tools/cancel_probe.py`

Run it in the gateway image through the `seed` service, with the lab that uses `compose.lab-process.json` (the engine is
`engine-minizinc:3000`, the proxy `web:8080`, both already in the `seed` environment):

```
lab_compose validate file=compose.lab-process.json
lab_compose up file=compose.lab-process.json      # with DEMO_SEED_TOOL=cancel_probe.py   (DEMO_SEED_ARGS empty or options below)
lab_compose seed
```

`lab_compose seed` uses the environment saved by the last `up` (`docs/DEMO.md`): change `DEMO_SEED_TOOL`/`DEMO_SEED_ARGS`
by repeating `up`. Equivalent with plain compose:
`DEMO_SEED_TOOL=cancel_probe.py DEMO_SEED_ARGS= docker compose run --rm --no-deps seed`. The lab must be seeded first
(`seed_lab.py`); put `DEMO_SEED_TOOL` back to `seed_lab.py` with another `up` before the next normal seed.

Options (all optional): `--time-budget-ms 600000` (what the engine may spend), `--cancel-timeout 90`,
`--running-timeout 120`, `--settle-timeout 60`, `--race-window 3`, `--tasks 150 --candidates 30`, `--user lab-owner`,
`--base-url`, `--engine-url`. Environment: `DEMO_SEED_PASSWORD` (required), `SMOKE_BASE_URL` (default `http://web:8080`),
`ENGINE_MINIZINC_URL` (default `http://engine-minizinc:3000`), `DATABASE_URL`, `CANCEL_PROBE_ENGINE_TOKEN` (only for an
engine that requires a bearer token; the lab's does not).

### What it does

1. Signs in as `lab-owner` (HTTP, like `smoke_lab.py`), uploads the hard package of `tools/engine_e2e.py` (150 tasks × 30
   candidates, a multiple-choice knapsack) as a snapshot and launches a `minizinc-csp` job (`exact-weighted`,
   `time_budget_ms` 600 000).
2. Waits until the job is `running` and the engine id of its attempt is in `job_engine_attempts` (the id is exposed by no
   route, so the row is read from the database with the gateway's own models), and checks that the engine, asked directly
   (`GET <engine>/internal/v1/jobs/{id}`), says that id is running.
3. Cancels the job through the API (`POST /v1/jobs/{id}/cancel`) and waits.
4. Checks, and reports each as a named check:
   * the job ends `cancelled`;
   * the cancellation **reached the solver while it was still working** (an engine that finished by itself before the
     gateway's `DELETE` is a failure);
   * the `job_engine_attempts` row of that attempt is `sent` (the engine confirmed with 200/204);
   * the engine reports **that same id** as cancelled (`failed` with an error starting `cancelled:`);
   * a `DELETE` sent by the probe answers `200 cancelled`, and a second one answers the same (idempotent).
5. Cleanup, outside the verdict: a job or an engine job still running is cancelled so the slot and the CPU are freed.

The probe sends its own `DELETE` only after it has read what the gateway left, so it cannot be the reason the engine job
is cancelled.

### Output and exit code

One JSON document on stdout: `tool`, `ok`, `classification`, `reason`, `job` (`id`, `engineJobId`, `attempt`,
`cancelState`), `checks` (`name`, `ok`, `detail`), `findings`, `timeline` (seconds), `cleanup`. Nothing secret is printed.

| `classification` | exit | meaning |
| --- | --- | --- |
| `passed` | 0 | every check held |
| `failed` | 1 | the cancellation did not work as it must; `checks`/`findings` say where |
| (config) | 2 | no `DEMO_SEED_PASSWORD`, or a non-positive size |
| `inconclusive` | 3 | the experiment could not be set up or did not stay valid: login/upload/launch refused (a binding space over the plan's limit, SPACE `pricing_unavailable`, concurrency), the job never ran, the id could not be read (no `DATABASE_URL`), **MiniZinc finished the job before the cancel** (or within `--race-window` seconds of it, where a finish cannot be told from a cancellation). Nothing is claimed about cancellation |

`inconclusive` is never a pass: if MiniZinc solves the package before the cancel, make it harder (`--tasks`,
`--candidates`) or give it more time (`--time-budget-ms`) and run again.

## Cancelling a job that is running (G2)

G1 found three gaps in the gateway that kept `POST /v1/jobs/{id}/cancel` on a `running` job from stopping the solver. They
are closed here.

### 1. The worker watches the flag while it waits for the engine

`POST /cancel` on a `running` job only sets `cancellation_requested` (the route is unchanged). The worker that runs the job
used to read the flag in `settle_engine_answer`, after `solve_remote` returned. Now `solve_remote` takes an `on_poll` hook,
awaited after every poll that finds the engine job still working, and `services/execution.py::CancelWatch` is that hook for
an engine whose registration declares the capability:

* Every `REMOTE_CANCEL_WATCH_INTERVAL_S` seconds (default `1`; `0` = every poll) it reads one column
  (`jobs.cancellation_requested`) in a short transaction that is committed at once. No connection or transaction stays open
  during the wait.
* On seeing the flag it checks the **lease** (`hold_lease`: a worker that lost it does nothing; the check after the solve
  discards its answer as before), then goes through the same door as every other cancellation:
  `remote_attempts.claim_one` (the claim is a compare-and-swap committed before any request, so the `DELETE` of an attempt is
  sent once even with a worker and the reconciler's sweep competing; the retries are the claim's backoff and bounded number
  of claims, R1-R5 untouched), `decide`, then `DELETE <endpoint of the attempt>/internal/v1/jobs/{engine id}`.
  `decide` has one new rule: the attempt that runs a job whose flag is set may be stopped (it is the only case in which the
  attempt that runs the job is). A newer attempt's id, a different endpoint, a missing capability are still refused.
* Outcomes, by what the engine says:

| The engine says | The job ends |
| --- | --- |
| `DELETE` 200 (`sent`) | `CANCELLED`, written only now, with the lease; the worker leaves the wait |
| `DELETE` 202 (stopping), then the poll shows `failed`, `cancelled: ...` | `CANCELLED`; the attempt row is settled `sent` |
| `DELETE` 202, then a later claim (after its backoff) answers 200 | `CANCELLED` |
| `DELETE` 404/405/501 (`skipped`: it cannot stop it) | nothing changes: the worker waits for the engine as before and reads the flag after the solve |
| nothing confirmed within `REMOTE_CANCEL_CONFIRM_TIMEOUT_S` (default `30`) of the first sighting | **`FAILED`, `engine_timeout`** (see below) |
| the engine finishes with a result first | `CANCELLED` (the flag is read after the solve, as always); the result is discarded; the usual door sends a `DELETE` for the finished job, which the engine answers idempotently |

* **Without the capability** (any registration that does not declare it, or whose OpenAPI does not describe the `DELETE`)
  no watch is installed: nothing is sent and the worker behaves exactly as before.
* **When the engine never confirms**, the job is **not** declared `CANCELLED`: the solver may still be running. This is the
  semantics B3/R1-R5 already had for an attempt the gateway gives up on (`engine_error` and friends): the job is failed
  and that is made durable first (`FAILED`, `code: engine_timeout`, the reason is logged with its correlation id; the flag
  `cancellationRequested` stays `true`), and only then is the attempt's cancellation tried once more. A claim that is not
  due yet stays `pending`/`failed` in `job_engine_attempts`; the job is terminal, so the reconciler's sweep may send it
  (`decide`: "the job is terminal"), within the usual bounded claims. The user can read the outcome (`failed`,
  `engine_timeout`, `cancellationRequested: true`) and retry the job once the engine is reachable.
* A result that an engine produces after the job ended is never accepted: `settle_engine_answer` and `fail_persisted_job`
  require the lease of a `running` job, and a `CANCELLED`/`FAILED` job has none. Cancelling twice is one cancellation (the
  flag is a boolean, the claim is unique per attempt); cancelling a finished job is `409 terminal_job`; another account gets
  `404`, as before. Nothing is charged or counted by this path: it writes no counters.

`ENGINE_CANCELLATION_BUILTIN`, `REMOTE_CANCEL_*` (`MAX_ATTEMPTS`, `DEFER_LIMIT`, `BATCH`, `CONCURRENCY`) keep their meaning.
The two new variables are read by `services/execution.py` directly (not by `Settings`).

### 2. The reconciler's sweep resolves the bundled registrations

`resolve_cancel_context` returned `None` for the `bim.builtin` namespace, so a lost attempt, or a `202` that needed a retry,
of a bundled engine ended `skipped`. It now rebuilds the registration the way the worker does for the job: the engine
manifest the job pinned in `provenance.engine`, and `installed_builtin_registration(manifest, engine_urls[engine], reference)`.
The endpoint is the gateway's configuration (`engine_urls`), never a value stored on or sent with the job, and a reference
the current installation no longer produces (another version or digest, another endpoint) gives no context, as before for any
revision that is gone: the attempt is `skipped` and nothing is sent.

### 3. Jobs queued before a deployment

See the deployment note above: documented as an operational step; not re-bound by the code.

## What is verified, and what is not

Verified here (no Docker, no engines in the worktree): the registration is generated as described (capability present for
`minizinc-csp`, absent for the others, switched by `ENGINE_CANCELLATION_BUILTIN`, validated, idempotent, a new immutable
version, schema-valid); the gateway's decision (`decide`) and the door every cancellation goes through send a `DELETE` to
`minizinc-csp` and to no engine that declares nothing; the rules R1-R5 of `tests/test_remote_cancel.py` are untouched; the
probe's logic against a simulated gateway, engine and database (`tools/tests/test_cancel_probe.py`: passed, job stays
running, engine finishes alone, race window, row not sent, not idempotent, setup refused, no database, job failed because the
stop was never confirmed). G2, in `tests/test_cancel_running_job.py` (SQLite; the whole path from the API through
`run_claimed_job`, `solve_remote` and `cancel_remote` against an asynchronous engine double): one `DELETE`, `CANCELLED` only
after the confirmation, 202 then the engine's own `cancelled:`, 202 then 200, an engine that never confirms (honest `FAILED`,
cancellation still open, finished by the sweep on the bundled registration), no capability = nothing sent, another account
refused, cancel racing the result, a late result that does not reopen the job, the rule of `decide`, and the bounded,
lease-fenced watch.

**NOT executed** here: the probe against the real lab (PostgreSQL, Dramatiq worker, nginx, real MiniZinc), and
`tests/concurrency/test_cancel_running_pg.py` (cancel vs finish with two sessions, one claim of the `DELETE` between the
worker and the sweep) needs PostgreSQL 16 (`TEST_DATABASE_URL`): it is skipped only when that variable is unset. Those runs
are the acceptance of this change and belong to the controller (`lab_compose`, above).

## Limits, and what the probe is expected to find

* **Java engines are opt-in.** Their `DELETE` exists only with `ENGINE_JOB_MODE=async`; the bundled registration declares
  nothing for them unless `ENGINE_CANCELLATION_BUILTIN` names them. The probe covers only `minizinc-csp`.
* **No exactly-once.** The cancellation is best effort and confirmed by the engine: `sent` is recorded only on a 200/204; a
  lost response or a crashed gateway leaves the row `failed`/`pending` and the gateway without a confirmation.
* **The id is lost if the engine restarts** (jobs are in memory): every old id is then `404`, the attempt ends `skipped`,
  and a solver the previous process started is no longer tracked.
* **A running job is cancelled within about `REMOTE_CANCEL_WATCH_INTERVAL_S` plus the engine's stop time** (G2, above), not
  when the solve returns. If the lab behaves otherwise the probe reports `failed` (`the job ends cancelled` false after
  `--cancel-timeout`, or `the cancellation reached the solver before it finished` false) with the matching `findings`: first
  check that the worker runs this version and that the registration of the job declares the capability.
* **An engine that does not confirm in `REMOTE_CANCEL_CONFIRM_TIMEOUT_S` leaves the job `failed` (`engine_timeout`), not
  `cancelled`.** The probe reports it as a failed check with the finding "did not confirm the stop"; MiniZinc normally answers
  the `DELETE` `200` once the solver is gone, or `202` and then reports `cancelled:` on the poll.
* **The sweep retries a bundled engine's cancellation** (G2, above); a reference the current installation no longer produces
  still ends `skipped`.
