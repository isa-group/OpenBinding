# OMG BPMN 2.0.2 XSDs: rights inventory

**State: NOT DEMONSTRATED (NO DEMOSTRADO).** Nothing in this repository shows that OMG allows the five XSD files to be
redistributed. For that reason Git does **not** version them (the files are *not versioned*): they are downloaded from
omg.org and verified at build time. They are, however, carried by the wheels, sdists, SDK and Docker images built from this
repository, and whether they stay there is a decision of the owner (below). The state is *not demonstrated* until the holder
records a clearance in `licenses.json`.

## What the files are

`packages/bim-core/src/bim_core/resources/vendor/omg/bpmn/2.0.2/` holds a `README.md` that says the files were "downloaded
unchanged on 2026-08-09" from <https://www.omg.org/spec/BPMN/20100501/> (index: <https://www.omg.org/spec/BPMN/2.0.2>), and
receives `BPMN20.xsd`, `Semantic.xsd`, `BPMNDI.xsd`, `DC.xsd` and `DI.xsd`. They are part of `compilerDigest` (it covers every
file under `resources/`), are read through `importlib.resources`, and are needed to validate BPMN workflows without network
access. The bytes are always the ones declared in `licenses.json`, wherever they came from, so `compilerDigest` and the goldens
do not depend on how the files arrived.

## How the files arrive

The five files are never listed by `git ls-files`: `.gitignore` (the root of OpenBinding and the one of `bim-toolchain`)
ignores them, `licenses.json` says `present_in_tree: false`, and `python3 tools/xsd_inventory.py --check` (also run by the
tests and by the lint job of the CI) fails if Git lists one or does not ignore it. `bim_core` does not download anything when
it is used (a change in `bim_core` would change `compilerDigest`); the download lives around it:

* `packages/bim-core/hatch_build.py` (standard library only, outside `src/bim_core`) is the one implementation. It downloads
  the five files over https from `source_base`, compares the SHA-256 of each with the declared one, and writes nothing unless
  all five match (temporary files and `os.replace`). It does nothing if the five are there and verify. Without network it
  stops with the exact command to run (`python3 <path>/hatch_build.py --ensure --directory <dir>`, or
  `python3 tools/xsd_inventory.py --ensure` in the toolchain).
* It is also the hatchling build hook of `bim-core` (`[tool.hatch.build.hooks.custom]`), so `pip install` from the sources,
  `pip install -e`, `uv sync` and `uv build` put the files in place before building. `[tool.hatch.build] artifacts` makes the
  wheel and the sdist carry them although Git ignores them, and the sdist carries `hatch_build.py` so that it can rebuild the
  wheel.
* `python3 tools/xsd_inventory.py --ensure` runs right after every `actions/checkout` of the workflows; the Dockerfiles of
  `bim-service`, `openbinding-gateway` and `experimentation/qacobench` copy `hatch_build.py` and run it before the install;
  `tools/xsd_session.py` (in the `conftest.py` files) runs it before a test session, and `packaging_support.ensure_xsd()`
  before anything is built; `tools/export_repo.py` downloads them into the copy where it runs the self-containment test.
  `python3 tools/xsd_inventory.py --fetch DIR` downloads them into another directory with the same verification.
* `tools/verify_release.py` and `tools/test_built_artifacts.py` compare the bytes of the five files inside the wheel and the
  sdist of `bim-core` with `licenses.json`. Nothing excludes the files from an artifact or from a release.

Reading of the table: none of the five files contains the words *copyright*, *license*, *licence*, *permission*,
*redistribute* or *all rights reserved*, the symbol (c) or the sign ©, and none contains an XML comment at all. The
earlier statement of `NOTICE.md` and of the vendored README, that the notices of OMG are "preserved byte for byte" in

(The official findings below name only `BPMN20.xsd` and `Semantic.xsd`; the other three are in the same situation as
served and vendored here. This is a reading of the files as present in this repository, not of what omg.org serves
today.)

## Official findings of the controller (`outputs/OMG_XSD_FINDINGS_20261014.md`), as received

Summary, verbatim from the contract that ordered this work:

> La página oficial BPMN 2.0.2 lista los 5 XSD sin enunciar licencia de redistribución; muestra «IPR Mode: RF-RAND»;
> `BPMN20.xsd` y `Semantic.xsd` tal como los sirve omg.org no traen comentario de copyright; los términos del PDF de la
> especificación (copia/distribución) no han sido leídos por el controlador; el estado es **NO DEMOSTRADO**.

In English: the official BPMN 2.0.2 page lists the five XSDs without stating a redistribution license; it shows
"IPR Mode: RF-RAND"; `BPMN20.xsd` and `Semantic.xsd`, as omg.org serves them, carry no copyright comment; the terms of the
specification PDF (copying and distribution) have not been read by the controller; the state is NOT DEMONSTRATED.

What this does and does not allow one to conclude: "RF-RAND" names the intellectual-property mode under which the
specification was adopted (royalty-free, reasonable and non-discriminatory terms for patents). It is not a copyright
license for the files and it does not say that they may be redistributed. The absence of a copyright comment in a file is
not a grant either. This repository does not read either as clearance. The full findings document is not part of this
repository and was not available to this work: only the summary above was.

## Options

Each of the four is a legal decision of the holder; none is taken here.

1. **Written confirmation from OMG** that the files may be redistributed with this repository, and under which terms.
   Record it in `licenses.json` (`cleared`, `cleared_by`, `cleared_on`, `evidence`). The record changes the state, not the
   mechanism: the files stay out of Git and are downloaded and verified at build time.
2. **Do not vendor; download from the official source and verify the SHA-256 at build time.** Implemented, as described in
   "How the files arrive". With the same bytes in place the `compilerDigest` is the one of this repository (it covers the
   bytes, not the way they arrived). This is what the repository does now. It removes the files from Git, not from the
   artifacts.
3. **Own validation**: replace BPMN validation by a schema written for this repository. Not done: it would change
   `bim_core` and therefore `compilerDigest` and every golden.
4. **Keep the repository private and accept the risk**: nothing is published or exported. The repository stays without the
   files in any case.

## What carries the files, and what is the owner's decision

The wheels, sdists, SDK and Docker images do carry the five files, downloaded with their SHA-256 checked during the build, so
that they work without network access afterwards; nothing excludes them from an artifact or from a release. Because the
rights are not demonstrated, **whether the files stay inside the artifacts and releases is a decision of the owner**; this
repository takes no position and does not decide it. If the owner decides that they must not ship, the change is in
`pyproject.toml` of `bim-core` (`artifacts`), in the Dockerfiles and in `compilerDigest`'s consumers: `bim_core` would need
another way to validate BPMN, which is option 3, and every golden would change.

## What would be needed from the holder

A decision among the four options and, for option 1, the written confirmation or the terms read (and who read them), and the
decision of the owner on shipping the files in artifacts. Until then the state stays NOT DEMONSTRATED (not demonstrated).
